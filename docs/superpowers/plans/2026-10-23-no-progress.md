# Repeated no-progress exploration fix

Root cause (verified from prior exploration.jsonl and last-tree.xml): after opening a drawer, 34 actions share one structural page key and one scroll candidate; semantic menu controls are not exposed as standard buttons. The runner only records dispatch, never measures outcome. Upstream graph retries remain eligible forever. This is a feedback/eligibility defect, not evidence that the C++ algorithm failed to compile.

Implementation:
1. A Foundation guard compares fresh accessibility observations after each operation. Fingerprints include meaningful label/selected/enabled/tree/quantized geometry, not text input values or timer-only changes. Block a context/target/direction after two no-effect outcomes. Block repeated identical transitions to bound A-B-A scrolling. Rejected targets are immediately excluded in their observation context.
2. Add per-call core exclusions before selection; temporarily filter the canonical state's action set, preserve graph/cache, prevent direct BACK fallback bypass, restore on return/throw. All excluded returns explicit NOP/no_available_action without consuming a model action.
3. Runner obtains next snapshot and audits effect; feeds exclusions into engine; only valid candidates reach execution. If all candidates exhausted, try available BACK; otherwise restart App without data clear at most two times, keep exclusion history. Exhaustion after recovery fails with no_progress_exhausted; never fill the remaining time with no-op swipes. An optional before/after effect is not business success.
4. Summary exports no-effect/changed/blocked/recovery counts and pending final outcome. Automated tests cover context/direction/cycle/jitter, before-policy filtering and restore. Run final signed source build + two-minute new-container measurement; inspect actual effects, longest same-context no-effect streak, action variety and explicit terminal state. No source/binary equivalence or business coverage claim.
